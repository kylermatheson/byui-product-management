# Set up the course repo

Guide a BYU-Idaho Product Management student using Codex or Claude. Ask one question at a time, explain each task in plain language, show commands before running them, and check what already exists so this procedure can resume. Never run a placeholder command. Never invent student answers or staff usernames.

1. Confirm the operating system, folder, and selected agent. Inspect README.md, AGENTS.md, course-prompts/, and sprints/. If this is the shared course website repo rather than the student's extracted starter, stop and direct the student to extract a separate starter folder. Avoid cloud-synced project folders. Preserve existing files and repository history.
2. Check git, gh, Node.js, and Python. Explain missing tools and help install them using their official instructions. Do not use sudo or install a package manager without asking. If restarting a terminal is needed, explain how to return and resume.
3. Ask the student to complete `gh auth login --hostname github.com --git-protocol https --web` themselves. Never request passwords, tokens, or one-time codes. Then check `gh auth status` and the GitHub username. Do not display credential files.
4. Ask the student to choose their own repo name. A suggestion is `<github-username>-product-management`; do not assume a NetID or course number. Confirm the exact owner and repo. Inspect whether this folder is already a git repo and where its remotes point before doing anything. If a repo exists remotely, inspect it and help clone it into a separate folder without overwriting work. For a new repo, initialize Git in the extracted starter, review and commit only the starter files, then show the student the exact `gh repo create <owner>/<repo> --private --source=. --remote=origin --push` command before asking to publish their initial commit. Never change an existing repo's visibility or remote without explaining and obtaining the student's agreement.
5. Ask for the Professor's and TA's supplied GitHub usernames. If blank, record that sharing is pending and continue the parts that do not need them. Once supplied, confirm the student wants those users invited, show `gh api -X PUT repos/<owner>/<repo>/collaborators/<staff-username>` with actual confirmed values, then invite each and verify pending or accepted access. Never add former staff or guessed usernames.
6. Confirm the agent is working inside the student's own project folder. Read README.md's Context section. Ask about the student's actual role and responsibilities, what they are working on, who it is for, and who uses their work, one question at a time. Roles may combine product, engineering, design, go-to-market, pricing, analytics, and operations. Record the student's words; "Not decided" is valid. Keep names, emails, and phone numbers of other people out of artifacts. Fill in Where the work lives with confirmed links only.
7. Read course-prompts/sprint-plan.md to prepare Sprint 1. Read course-schedule.json: Sprint 1's plan is written and submitted during the first class, and its wrap-up is due Saturday, February 27, at 23:59 America/Boise. Do not invent a first-class date while the meeting pattern is unconfirmed.
8. Review the diff with the student and commit only their intended files. Ask for submission approval before pushing to their confirmed private repo. Verify files on GitHub after any authorized push. Report the repo URL, plan URL, sharing status, and any unfilled course details. Remind the student to submit required links using the supplied LMS instructions. Do not claim a submission or invitation succeeded without verifying it.
