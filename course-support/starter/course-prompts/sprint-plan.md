# Sprint plan

Read AGENTS.md, README.md, and course-schedule.json. Ask which sprint (1–6). Use the schedule's sprint dates: all six occupy one week each, and wrap-ups are due Saturdays, February 27 through April 3, at 23:59 America/Boise. Plans for Sprints 2–6 are due the preceding Saturday. Sprint 1's plan is written and submitted during the first class, the only exception. Meeting days and times are still unconfirmed, so do not invent an exact first-class date. Use the current published course schedule if staff have updated these dates.

Read any existing `sprints/sprint-N-plan.md` before editing. Ask the student one question at a time for Goal, Why this, Done looks like, and Predicted difficulty (1 to 5). Use templates/sprint-plan.md for the file shape. The goal and choices must come from the student; do not write their answers for them. Clarify vague answers without proposing a goal as if it were theirs. Output may be code, research, design, pricing, copy, an automation, or other real checkable work on any builder axis.

If changing an existing plan, ask what changed and why. Preserve its history and add a dated Changes note. Never silently replace earlier commitments. Do not resubmit an unchanged link.

Save the plan, show the diff, and help the student commit that file. Before pushing, confirm the student's actual repository and obtain their submission approval. Verify the plan exists on GitHub after an authorized push. Provide its URL for the LMS Plan assignment. Difficulty is not graded; all four fields must contain the student's answers. Never invent a deadline, submit placeholder work as complete, or push unrelated files.

Use evidence from the previous sprint when preparing the next plan. The weekly class topic is a tool for learning, not a requirement to add an unrelated feature to the student's goal. The plan is the Prepare step for the work ahead; reflection belongs in the existing review, not a new assignment.
